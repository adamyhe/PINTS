## I/O, memory and pool follow-ups to the parallel engine

Stacked on the parallel-engine PR (`pr/03b-gate1-engine`); review only the last 13 commits.

**The output is byte-identical to the base branch.** Two intermediate files change form; neither is a result, and
both are deleted at the end of the run (see below).

### Why

On the base branch, a run held more memory than its data needed, wrote and kept tens of gigabytes of temporary
files, and left a few long steps on one process. Measured on `gate1` (`f8110c7`, see Timing for how it relates to
the base branch):

- **The replicate merge was the memory peak.** It loaded whole chromosomes and cast them to int32, and it kept the
  merged plus strand while merging the minus strand. H1 (two BAM replicates) peaked at 20.7 GB PSS at 16 threads
  and 21.0 GB at 64 threads.
- **One-thread runs loaded whole chromosomes as float64.** Control normalisation and the bigWig loader did this at
  one thread only; the parallel forms already worked block by block. H3 (BAM with control) peaked at 5.0 GB, and
  T3 (bigWig) at 3.4 GB.
- **Coverage dumps stayed on disk until the end.** An H1 or H3 run writes about 37 GB of per-chromosome `.npy`
  dumps (1176 files; profile of `6d2056c`, which writes the same dumps). All of them were deleted in the final
  housekeeping, though most stop being read much earlier.
- **Serial steps.** Each strand's stratified-filtering table was written by one worker: `to_csv`, then
  `index_bed_file`, which re-sorts the file with `bedtools sort`, copies it, bgzips it and indexes it. Pairing ran
  in the main process. The largest BAM contig set the length of contig-parallel parsing.
- **Copy-on-write in the pool.** Each worker's cyclic GC walked every object inherited from the parent and wrote
  to its header, so the parent's pages were copied into every worker.

### What changes

Memory:
- **Replicates are merged block by block** (`NPY_BLOCK` pieces, the same element-wise operations). The blocks are
  written in the widest input dtype while the maximum is taken. The file is rewritten only if the dtype chosen
  from that maximum differs, so the result is the same file either way. Inputs that are not plain 1-D integer
  `.npy` files of one length use the original code.
- **One-thread normalisation and bigWig loading use the block-wise code.** The parallel forms already run their
  tasks inline when `threads <= 1`, and they keep the same dict order, zero tracks and warnings. The dense bigWig
  loader stays for pyBigWig builds without numpy support.
- **The parent's objects are frozen for the GC while the pool forks** (`gc.freeze`), and unfrozen afterwards.

Disk:
- **Coverage dumps are deleted once nothing reads them**, on a background thread:
  - per-replicate dumps, once merged;
  - un-normalised sample and control dumps, once normalised;
  - the remaining dumps, once every strand is evaluated and its filtering has been dispatched.

  `release_coverage_files` skips any path still referenced by a live coverage dict. With a pool, the first two
  sets are queued until phase 2's tests start, because phase 2 writes no files; deleting 24 GB while element
  definition was writing its bgzip and tabix files slowed those writes about twofold. Single-threaded runs delete
  them at once. Housekeeping joins the threads before its own pass.
- **Subpeak beds stay in memory.** Element definition, when called from the pipeline, leaves its per-chromosome
  subpeak beds plain, since phase 1 reads them once from start to end. Phase 1 writes, bgzips and indexes its
  subpeak bed only when the in-memory `SubpeakIndex` rejects the lines and phase 2 needs the tabix fallback.
  `unified_element_definition` keeps its default (compressed) behaviour.

Parallelism:
- **The stratified-filtering table is written in parallel chunks, without `bedtools sort`.** The table is already
  sorted by chromosome and start, the keys `bedtools sort` uses. When no (chromosome, start) pair repeats, the
  sorted file is the table as written: the pool formats row chunks with `to_csv`, BGZF-compresses them, and the
  parts are concatenated and given the same CSI index. Each step is submitted from the previous one's callback,
  so the two strands proceed at once. With repeated keys, the original writer runs, so `bedtools`' order for ties
  is kept.
- **Large BAM contigs are split into regions** when parsing with several threads. A region counts the reads that
  start in it, so every read is counted once, and the per-contig check against the index statistics still holds.
  Counts are summed per contig in uint32, as the original counters do. Single-threaded parsing is unchanged.
- **Phase-2 chunks are built from the subpeak bounds.** Phase-1 workers already parse each subpeak's start and
  end; they now return them as int64 arrays. The main process cuts segments and selects each chunk's context with
  numpy instead of splitting every line again. The chunks and contexts are the same as before.
- **The two strands are paired on the pool.** They only read each other's candidate files, which are written
  before pairing. The emptiness checks of the pairing outputs stop at the first record, with pybedtools' rules for
  headers and blank lines, instead of counting every record up to three times.

Two intermediate files change: the stratified-filtering `.gz` holds the same lines in a different BGZF block
layout, and the subpeak beds are no longer compressed and indexed when phase 2 does not need them.

The stratified-filtering change also assigns the result of its final `sort_values` instead of sorting in place
(`inplace=True` is deprecated in pandas 3.1 and removed in pandas 4; the frame is local).

### Testing

- New and extended tests:
  - `tests/diff/test_differential_memory.py`: merged files, read counts and their dtypes equal `pints_ref`'s for
    2–3 replicates of mixed dtypes, tiny blocks, dtype boundaries and int32 wrap-around; the serial path; the
    length-mismatch fallback.
  - `tests/unit/test_release_coverage_files.py`: live paths are kept, other dumps are gone by the time
    housekeeping returns, missing files are ignored, and deferred deletions wait until they are started.
  - `tests/diff/test_differential_filtering_write.py`: decompressed content and tabix lookups equal
    `stratified_filtering`'s for random tables, chunk counts and `--disable-small`; tables with ties or no rows use
    the original writer; errors surface on `get()`; BGZF round trips at block boundaries.
  - `tests/diff/test_differential_gate1.py`: contigs split into regions give the same dumps, including reads that
    straddle region bounds; the regions cover the contig.
  - `tests/diff/test_differential_engine.py`: chunks built from the bounds equal those from line parsing; subpeak
    beds are written only when the tabix fallback needs them; plain element definition equals the compressed one.
  - `tests/diff/test_differential.py`: pairing on the pool equals `pints_ref`; the emptiness check agrees with
    `BedTool.count()`.
- Full suite at this branch's head (`0333d58`): 251 passed.
- chr22 test data, with bigWig, BAM, and `--annotation-gtf --focused-chrom chr22` input, at 1 and 4 threads: the
  bidirectional, divergent and unidirectional peaks are byte-identical to `main`. (`main` ignores
  `--focused-chrom`, which PR 2 fixes, so for the GTF case it is given the chromosome through its API.)
- Benchmark equivalence of `6d2056c`: all 134 runs (19 datasets; default, `--disable-small` and sensitive
  configurations; 1 to 64 threads) are byte-identical to `main`.
